# Защита от автоматических запросов

Внешняя капча отключена по выбору владельца. Абсолютной защиты от ботов нет:
браузерная автоматизация способна получить CSRF-токен и имитировать действия человека.
Распределённый DDoS требует фильтрации у провайдера до сервера.

## Реализовано

- IP определяется по непосредственному соединению; X-Forwarded-For принимается только
  от адресов `TRUSTED_PROXY_CIDRS`, цепочка разбирается справа налево. IPv6 /64 имеет
  общий бюджет. Заголовок User-Agent не даёт поисковым роботам особых прав.
- Общие атомарные Redis-счётчики для всех вариантов одной операции:
  заявки — 5/минуту, 20/час; чат вместе со сбросом истории — 10/минуту, 60/час.
  Новый cookie или другой URL формы не сбрасывает счётчик.
- POST чата дополнительно ограничен 150 попытками/IP/сутки и 1000 на сайт/сутки.
  Это предохранитель нагрузки, не точный денежный бюджет. Неудачные запросы после
  проверки CSRF тоже учитываются. Дневное окно — UTC.
- Одновременные ответы чата: один/IP, шесть на сайт; Redis-аренды освобождаются при
  закрытии ответа и истекают через 90 секунд при аварии процесса. Внешние AI-запросы
  не повторяются автоматически, имеют таймаут 15 секунд; поток ограничен временем
  и 1024 выходными токенами. Клиент не отправляет второе сообщение до конца потока.
- Анонимные POST требуют CSRF cookie, токен и корректный Origin/Referer; это защита
  от отправки с чужого сайта, а не доказательство, что посетитель человек.
- JSON тела до 16 КиБ; ограничены сообщения и поля контекста чата. Телефон и явное
  согласие обязательны. Honeypot и существующие эвристики отсеивают простой спам.
- Резервирование нормализованного телефона атомарно: повторная заявка в течение
  пяти минут не создаёт дубль. Префиксы 8 и +7 распознаются как один номер.
- Вход в админку: 10 попыток/5 минут, 30/час/IP. Автоматическое создание `admin/admin`
  удалено. Пароли существующих пользователей не меняются.
- Отказ защитного Redis возвращает 503 для защищённых операций. Публичные страницы
  не требуют капчи и не блокируются этим механизмом. 429 содержит Retry-After.
- Backend :8001 и frontend :3000 в Compose привязаны к 127.0.0.1.

Счётчики фиксированных окон могут пропустить до двойного лимита вблизи границы
окна. Nginx добавляет непрерывное ограничение частоты и параллельных соединений.
Общие IP офисов/мобильных операторов делят лимиты; при жалобах проверять логи 429.
Redis должен оставаться доступным и не подвергаться очистке/вытеснению ключей.
Перезапуск Redis сбрасывает текущие лимиты: сохраняйте AOF/RDB, если требуется
непрерывный суточный бюджет, и настройте оповещение о перезапусках/нехватке памяти.

## Параметры развёртывания

В существующий `.env` добавляются только новые строки, секреты не заменяются:

```dotenv
TRUSTED_PROXY_CIDRS=172.18.0.1/32,127.0.0.1/32
SECURE_COOKIES=True
TRUST_PROXY_HTTPS=True
CHAT_IP_DAILY_LIMIT=150
CHAT_GLOBAL_DAILY_LIMIT=1000
CHAT_MAX_CONCURRENT=6
```

Адрес `172.18.0.1` подтверждён для текущего Docker bridge на 194.113.35.110.
На другом сервере определить его заново. Не доверять всей сети или всем источникам.
Nginx должен **перезаписывать** X-Forwarded-For и X-Forwarded-Proto; прямые порты
приложения должны быть закрыты извне. В локальной HTTP-разработке secure cookies
и доверие HTTPS-прокси выключены.

Файлы `deploy/nginx/` — заготовки для слияния с действующей конфигурацией.
Не заменять ими весь `/etc/nginx/nginx.conf`. Сохранить сертификаты, существующие
маршруты, `/media/`, `/static/`, `/_next/static/` и ACME. Проверить `nginx -t` перед reload.

### Особенность действующего сервера

На 2026-10-04 цепочка HTTPS: Xray/Reality :443 → Nginx stream :444 → Nginx TLS :446.
В Reality `xver=0`, поэтому HTTP Nginx получает адрес 127.0.0.1 вместо посетителя.
**Не включать строгие лимиты по IP, пока реальный адрес не передаётся по всей цепочке.**

Подготовлен `deploy/haproxy-realip.cfg`: отдельный локальный relay :1444 принимает
PROXY protocol от Xray и передаёт его только в TLS-сервер сайта. Остальные маршруты
сохраняют прежние адреса и формат TCP. Для активации нужны:

1. Проверенный relay на 127.0.0.1:1444.
2. Для сайта: добавить `listen 127.0.0.1:8446 ssl proxy_protocol`, сохранив старый :446,
   `set_real_ip_from 127.0.0.1`, `real_ip_header proxy_protocol`.
3. В сохраняемой настройке Xray: target → 127.0.0.1:1444, xver → 2.
4. Короткий перезапуск Xray и проверка сайта, других SNI-маршрутов и реального IP.

Этот шаг затрагивает общий Xray/VPN, поэтому согласуется отдельно. Исходный stream
:444 остаётся для возврата. Редактирование только сгенерированного config.json
не сохраняет изменения после следующего запуска панели.

## Группы безопасности Cloud.ru

- Для HTTP/HTTPS нужны отдельные TCP 80 и TCP 443, не диапазон `80:443`.
- SSH 22 ограничивать внешним IP администратора/VPN, сохраняя резервный доступ
  через консоль Cloud.ru; сначала проверить новую SSH-сессию.
- 3000, 8001, PostgreSQL 5432 и Redis 6379 не публиковать.
- 8000 на текущем сервере занят отдельным GoHTTPServer, RustDesk и Xray тоже работают
  отдельно. Не закрывать их порты без решения владельца этих сервисов.
- DNS 53 нужен извне только при обслуживании публичного DNS. Проверить назначение
  правила, прежде чем удалять его. Правила IPv6 проверяются отдельно.

## Проверка

```bash
cd backend
python manage.py test core.tests apps.seo.tests --settings=core.test_settings
```

Для проверки атомарности и аренд с настоящим Redis запустить **отдельный** временный
экземпляр и добавить `PILIGRIM_TEST_REDIS_URL=redis://127.0.0.1:16379/1`.
Тесты очищают тестовый cache; нельзя указывать рабочий Redis.
