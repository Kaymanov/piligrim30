# Обновление существующего сервера с сохранением данных

Проверенная установка: `kayal@194.113.35.110:22`, проект `/opt/piligrim30`,
Compose project `piligrim30`, PostgreSQL volume `piligrim30_postgres_data`,
изображения `/opt/piligrim30/backend/media`, настройки `/opt/piligrim30/.env`.
На этом сервере опубликован **test.piligrim30.ru**; его SITE_URL остаётся тестовым.
Подключение основного домена и разрешение его индексации — отдельный шаг.

## Порядок

1. Сравнить рабочий Git HEAD и изменённые файлы. Локальные серверные изменения
   сохранять; автоматически не выполнять reset/clean. Проверить свободное место.
2. Создать копию `deploy/backup.sh LIVE BACKUP_ROOT` вне каталога сайта. Скрипт
   проверяет Compose project и привязку backend, делает pg_dump, копирует код,
   media, .env и Nginx; проверяет читаемость архивов и SHA-256. Он не останавливает
   записи — финальная копия создаётся в режиме обслуживания.
3. Восстановить dump в **отдельную временную БД**, проверить количество записей.
   Применить новые миграции к этой копии и повторно проверить данные.
4. Собрать оба новых образа из отдельного release-каталога, до переключения сайта.
   Проверить целостность переданного кода. Сохранить старые image ID и теги.
5. Проверить передачу реального IP по всей цепочке прокси (см. SECURITY.md).
6. Подготовить Nginx-конфигурацию, сохранить предыдущую, выполнить `nginx -t`.
   В серверном шаблоне предусмотрен файл `/opt/piligrim30/.maintenance`, при наличии
   которого сайт возвращает 503. Это временно закрывает также заявки и админку.
7. Включить обслуживание, остановить **только backend и celery_worker**, сделать
   финальный backup. PostgreSQL и Redis остаются запущенными. Зафиксировать хеши
   строк существующих таблиц и файлов media, чтобы проверить их после обновления.
8. Установить только файлы из проверенного manifest через `apply-code.py`.
   Он сверяет старые и новые SHA-256 **до изменений** и сохраняет отдельный архив
   старого кода для отката. В manifest нельзя включать `.env`, `.git`, media и venv.
9. В существующий `.env` добавить только согласованные параметры защиты и SITE_URL.
   Сохранить DJANGO_SECRET_KEY, пароли, API-ключи и настройки БД/почты.
10. Переключить frontend/backend/celery на собранные образы командой
    `docker compose up -d --no-deps --no-build backend celery_worker frontend`.
    Entrypoint применяет миграции и прекращает запуск при ошибке.
11. Проверить backend health, реальный frontend, админку, robots/sitemap, отказ
    форм без CSRF, правильный IP и приватность портов 3000/8001. Сравнить данные.
    Снять обслуживание; повторить публичную проверку HTTPS и журналов ошибок.

Не использовать `down -v`, удаление/пересоздание рабочего PostgreSQL volume,
`flush`, загрузку demo fixtures или `rsync --delete` по рабочей папке.

## Возврат

Если проверка приложения не прошла, оставить обслуживание, остановить новые
backend/celery/frontend, вернуть **только старый код** из `previous-code.tar.gz`,
удалить только новые пути из соответствующего manifest и вернуть старые образы.
При возврате `.env` использовать сохранённый файл; сертификаты и media не заменять.
Добавочные SEO-таблицы можно оставить: старый код их не использует. Не откатывать
миграции и не восстанавливать рабочую БД поверх новых заявок автоматически.

Для возврата маршрута Xray изменить **только** target обратно на `127.0.0.1:444`
и xver на 0 в сохранённой настройке inbound :443; перезапустить Xray. Старый
Nginx listener :446 сохранён. Строгие лимиты по IP при старом маршруте необходимо
отключить, иначе все посетители будут считаться одним IP. Полную базу панели Xray
поверх текущей не восстанавливать: это могло бы затереть новые настройки клиентов.

Резервные копии содержат персональные данные и секреты; права каталога 0700,
файлов 0600. Дополнительная локальная копия разрешена владельцем отдельно.
