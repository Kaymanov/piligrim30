# Plan 03-01: Email-уведомления и Защита форм

## Goal

Реализовать отправку email-уведомлений при создании заявки и многослойную защиту форм (honeypot, валидация, дедупликация, timestamp trap, behavioral trap, CSRF).

## Context

**Текущее состояние:**

- Модель `Lead` полностью реализована (name, phone, email, debt_amount, UTM, status, lead_type)
- `LeadSerializer` автоматически записывает IP и User-Agent
- `LeadViewSet` с actions: create, quiz, callback
- Rate Limiting 5/min (AnonRateThrottle) уже работает
- SMTP-переменные есть в `.env.example` (EMAIL_HOST, EMAIL_PORT, etc.)
- Django CSRF middleware уже в MIDDLEWARE (но DRF по умолчанию exempt для API)

**Что нужно сделать:**

- Настроить Django email backend
- Отправлять email при каждом создании Lead
- Добавить honeypot-поле в сериализатор
- Добавить серверную валидацию (phone format, required phone, consent)
- Добавить дедупликацию (Redis-based, phone + 5 min)
- Добавить timestamp validation (< 3 sec = reject)
- Добавить behavioral flag validation
- Настроить CSRF для form endpoints (endpoint для получения токена)

### 5. Дедупликация (Redis)

**File:** `backend/apps/leads/serializers.py` или `backend/apps/leads/services.py`

Логика:

- При валидации проверить Redis key `lead_dedup:{phone_normalized}`
- Если ключ существует → raise ValidationError "Заявка уже отправлена, попробуйте позже"
- После успешного создания → set key с TTL 300 секунд (5 мин)
- Нормализация телефона: убрать пробелы, дефисы, скобки

**Verification:** Первый POST → 201. Второй POST с тем же телефоном через 1 сек → 400. Через 5+ мин → 201.

---

### 6. Timestamp Trap

**File:** `backend/apps/leads/serializers.py`

Логика:

- Фронтенд отправляет поле `_ts` (timestamp загрузки формы в unix ms)
- Сериализатор проверяет: `now - _ts < 3000ms` → reject
- Поле `_ts` — write_only, не сохраняется в модель
- Если `_ts` отсутствует — пропускаем проверку (graceful degradation для API-клиентов)

**Verification:** POST с `_ts` = now → 400. POST с `_ts` = now - 5000 → 201.

---

### 7. Behavioral Trap

**File:** `backend/apps/leads/serializers.py`

Логика:

- Фронтенд отправляет поле `_hid` (hashed interaction digest) — любое непустое значение означает "пользователь взаимодействовал"
- Сериализатор проверяет: если `_hid` пустое или отсутствует → reject (если `_ts` тоже присутствует, т.е. фронтенд поддерживает эти поля)
- Поле write_only, не сохраняется
- Graceful: если ни `_ts` ни `_hid` не переданы — пропускаем обе проверки (API без фронтенда)

**Verification:** POST с `_ts` но без `_hid` → 400. POST с `_ts` + `_hid` → 201.

### 8. CSRF для Form Endpoints

**File:** `backend/apps/leads/views.py`, `backend/core/urls.py`

Логика:

- Создать endpoint `GET /api/v1/csrf/` который возвращает CSRF-токен в cookie
- На LeadViewSet убрать `@csrf_exempt` (DRF SessionAuthentication уже проверяет CSRF)
- Добавить `SessionAuthentication` в authentication_classes для LeadViewSet
- Фронтенд будет: 1) GET /api/v1/csrf/ → получить cookie, 2) POST с `X-CSRFToken` header

**File:** `backend/apps/leads/views.py`

```python
from django.middleware.csrf import get_token
from rest_framework.decorators import api_view
from rest_framework.response import Response

@api_view(['GET'])
def get_csrf_token(request):
    return Response({'csrfToken': get_token(request)})
```

**Verification:** POST без CSRF token → 403. POST с валидным CSRF → 201.

## Verification Criteria

- [ ] POST /api/v1/leads/ с валидными данными → 201 + email
- [ ] POST с заполненным honeypot (`website`) → 400
- [ ] POST без phone → 400
- [ ] POST с consent_accepted=false → 400
- [ ] POST с невалидным phone → 400
- [ ] Повторный POST с тем же phone < 5 мин → 400
- [ ] POST с \_ts = now (< 3 sec) → 400
- [ ] POST с \_ts + без \_hid → 400
- [ ] POST без CSRF token (когда SessionAuth активен) → 403
- [ ] Gemini API недоступен → email всё равно отправляется (независимые системы)
